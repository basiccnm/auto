# 1. 🔴 `community_posts`가 삭제 연쇄에서 빠져 있었습니다

로컬 D1에서 `child_id`를 가진 테이블을 **전수 조회**했습니다. 코드를 읽고 짐작한 게 아니라
`sqlite_master`에서 뽑았습니다.

| 테이블 | 연쇄 포함 여부(수정 전) |
|---|---|
| `records` · `activity_schedules` · `identifiers` · `personal_schedule` · `personal_events` · `schedule_settings` | ✅ |
| **`community_posts`** | ❌ **빠져 있었음** |
| `orders` | ❌ (의도적 — §3) |

`community_posts`는 학교 커뮤니티 글이라 "자녀 데이터"로 안 보이지만, 실제로는

```sql
child_id INTEGER NOT NULL REFERENCES children(id),
owner_token TEXT NOT NULL,      -- 작성자 식별
display_name TEXT,              -- 커뮤니티 닉네임 스냅샷
author_grade TEXT, author_class TEXT   -- 작성 당시 학년·반 박제
```

를 **함께 박제해 보관**합니다. 자녀를 지워도 이게 남으면
*"언제든 원본까지 전부 삭제"* 라는 사용자 약속이 그대로 깨집니다.

→ `deleteChildCascade`의 batch 배열에 추가했습니다.
주석에 **판별 기준을 못박아 뒀습니다** — "개인 데이터로 보이는가"가 아니라
**`child_id`를 들고 있는가**. 이번에 놓친 이유가 정확히 그 착각이었습니다.

# 2. 그 외 이번에 합류·보강한 것

## ① `index.js`의 기록 단건 삭제가 아직 인라인이었습니다

`handleRecordDelete`가 `r2KeysOf`는 공용 걸 썼지만 **삭제 순서 자체는 자기가 다시 쓰고**
있었습니다(`R2 삭제 → 실패 시 중단 → D1 삭제`). `data_children.deleteRecordAssets`와 같은 로직 두 벌.
→ 공용 함수 호출로 교체. 소유권 확인 SQL은 그대로 뒀습니다(그 함수는 "이미 확인된 record만 받는다"가 계약).

## ② R2 삭제 실패를 조용히 삼키고 있었습니다

`catch (e)`가 `console.error` 없이 `{ok:false}`만 돌려주고 있었습니다.
사용자에겐 500만 보이고 **왜 실패했는지 추적할 방법이 없습니다.** 두 함수 모두 로그를 남기게 했습니다.

## ③ `childId` 문자열/정수 — admin 삭제가 **조용히 0건 처리**되고 있었습니다

> ⚠️ 이 건과 §2-②의 일부는 **제가 쓴 코드가 아니라 세션 중 파일에 들어와 있던 수정**입니다.
> 되돌리지 않고 그대로 두고, 대신 **실제로 동작하는지 검수에 포함**했습니다(§4-D).

D1의 `bind()`는 넘긴 타입을 그대로 보냅니다. 라우터 정규식이 준 문자열 `"99"`를 그대로 쓰면
`INTEGER` 컬럼과 매칭되지 않아 **삭제가 0건인데 `ok:true`가 반환**됩니다.
API 경로는 DB에서 읽은 정수를 넘겨 우연히 동작했고, **admin 경로만 실패**하고 있었습니다.
게다가 `handleAdminDeleteChild`가 반환값을 무시해 **302로 넘어가 "삭제됐다"고 보였습니다.**
→ 함수 입구에서 `Number()` 강제 + admin 호출부에서 반환값 확인.

**조용한 실패가 가장 나쁩니다.** 사용자는 지웠다고 믿고, 데이터는 남아 있습니다.

# 4. 검수 결과 — 전부 통과

`.wrangler/tmp` 낡은 빌드 4개(3.2MB) 비우고 dev 새로 띄운 뒤 실행했습니다.
`.wrangler/state`(683MB, 로컬 D1·R2 실데이터)는 건드리지 않았습니다.

> **삭제 검증은 `--local`로 돌렸습니다.** 평소 쓰시는 `--remote`는 **진짜 R2·D1을 지웁니다** —
> 자녀 삭제 테스트를 거기서 하면 실제 사진이 사라집니다. 검수 끝나고 `--remote`로 되돌려놨습니다.

## A. 자녀 연쇄 삭제 — 7개 테이블 + R2

검수용 자녀를 하나 만들고 **딸린 테이블 7곳에 각각 1행씩** 심었습니다. 실제 이미지도 업로드했습니다.

| | 삭제 전 | 삭제 후 |
|---|---|---|
| `children` · `records` · `activity_schedules` · `identifiers` · `personal_schedule` · `personal_events` · `schedule_settings` | 각 1 | **각 0** |
| **`community_posts`** | 1 | **0** ← 이번 수정의 핵심 |
| R2 원본 `rec/94/5b6d9564-…` | 46,808 B | **The specified key does not exist** |
| R2 파생 `…_t` | 7,084 B | **The specified key does not exist** |

파생(`_t`)까지 사라진 게 `R2_DERIVED_SUFFIXES`가 실제로 따라갔다는 증거입니다.

## B. 삭제 경로 4개 전부

| 경로 | 결과 |
|---|---|
| 웹 `POST /child/delete` | 302 → 연쇄 완료 |
| API `DELETE /api/v1/children/{id}` (재인증 없이) | **403 `REAUTH_REQUIRED`** — 잠김 확인 |
| API 같은 요청 + `X-Reauth-Token` | 200 `{deleted:true}` → 연쇄 완료 |
| **admin `POST /admin/members/{id}/delete`** | 302 → 연쇄 완료 (`community_posts` 포함 0) |

**admin 경로는 §2-③ 수정 전이면 조용히 실패했을 자리입니다.** 그래서 일부러 넣었습니다.

## C. 기록 단건 삭제 (제가 바꾼 코드)

## 6.1 반영 — 삭제 확인 화면 경고 (지시대로 처리)

**① 자녀 개별 삭제** (`templates.js` `childrenManagePage`)

```
○○ 자녀를 삭제할까요?
이 자녀 이름으로 쓴 학교 커뮤니티 글도 함께 지워집니다.   ← 추가
남은 이용기간은 환불되지 않습니다.
```

글이 있든 없든 **항상** 띄웁니다. 누르기 전에 알아야 의미가 있고, 있는지 여부는 누른 뒤에나 압니다.

**② 전체 삭제**(`/mypage/purge`)도 함께 고쳤습니다.
이 화면은 *"지워질 것을 실제로 세어 보여준다"*가 원칙인데 **커뮤니티 글만 그 목록에서 빠져 있었습니다.**
실제로는 지워지므로 그대로 두면 화면이 거짓말을 합니다.

```
· 자녀 1명의 프로필과 이름
· 업로드한 기록 N건 — 원본 사진 포함
· 방과후·활동 일정 N개
· 학교 커뮤니티에 쓴 글 N건       ← 추가 (0건이면 줄 자체를 숨김)
· 시간표 개인 설정·개인일정 전부
```

`handlePurgeAll`(`index.js`)에 카운트 질의 1개를 더했습니다.

**검수:** 로컬에서 자녀 1명 + 커뮤니티 글 1건을 심고 두 화면을 실제로 렌더해 확인했습니다.

| 화면 | 확인 |
|---|---|
| `/mypage/children` 삭제 버튼 | confirm 문구에 커뮤니티 글 경고 **표시됨** |
| `/mypage/purge` | 목록에 `학교 커뮤니티에 쓴 글 1건` **표시됨** |

검수 데이터는 회수했습니다(자녀 0 · 글 0 · users 0).

`/mypage/purge`가 자녀 연쇄만 돌고 아래를 남깁니다. 사용자는 "전부 삭제했습니다" 화면을 봅니다.

# 7. 다음 단계(②)에 넘길 것 — 조사 중 확인된 잔여

| 항목 | 현재 |
|---|---|
| `isSubscriber` | **아직 쿠키 판정**(`subscriber=1`). orders 기반으로 교체 필요 |
| 판정 기준 주의 | `children.trial_expires_at`은 **7일 무료체험도 포함**이라 "유료" 판정에 쓰면 안 됩니다. `orders`에서 `status='active' AND expires_at > now`로 봐야 합니다 |
| `AUTH_EXPIRED`/`AUTH_INVALID` | `resolveOwner`가 `auth.error`를 버려 **전부 `AUTH_REQUIRED`로 나갑니다.** 계약 §1.3대로면 앱이 refresh를 시도해야 하는데 지금은 로그인 화면으로 튕깁니다 |
| 쿠키만 있는 기존 사용자 | `accounts` 행이 없어 `requireReauth`가 `AUTH_REQUIRED`를 냅니다 → **API로는 수정·삭제가 아예 불가.** 의도인지 확인 필요 |
| 인증 중복 조회 | 라우터가 `resolveOwner` 1회 + `requireReauth`가 다시 `resolveAuth` 1회. 한 번만 풀어서 내려주면 요청당 DB 조회 2회가 줍니다 |
| `AUTH_SECRET` | 여전히 개발용 상수. **배포 전 `wrangler secret put AUTH_SECRET` 필수**(회신19 §2-3) |

**배포 안 합니다.** 라이브 차단·`wrangler deploy` 금지 유지 중입니다.

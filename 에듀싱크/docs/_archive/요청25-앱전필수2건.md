# 1. ① 회원 탈퇴 API — `DELETE /api/v1/me` 신설

계약 §3.2에 추가했고(개정 주석 포함), §3.4 재인증 목록에도 올렸습니다.

**웹 `/mypage/purge`와 완전히 같은 파기 경로**(`data_accounts.withdrawAccount`)를 탑니다.
탈퇴 구현이 두 벌이 되면 표가 늘 때 한쪽만 고쳐집니다 — 삭제 연쇄와 같은 단일 진입점 원칙.

되돌릴 수 없는 요청의 끝판이라 **access + reauth 둘 다** 요구합니다.

## 검수 (자녀 1명 + 실제 이미지를 딸린 계정으로)

| 요청 | 결과 |
|---|---|
| reauth 없이 DELETE | **403 `REAUTH_REQUIRED`** |
| 무인증 | 401 `AUTH_REQUIRED` |
| reauth 첨부 | **200** `{withdrawn:true, purged:{children:1}}` |
| 탈퇴 후 같은 access로 `/me` | 401 `AUTH_INVALID` (묘비는 active 조회에 안 잡힘) |
| DB | 자녀 0 · 기록 0 · **status='withdrawn'** · email NULL · auth_methods 0 · 옛 토큰 조회 0 |
| R2 | 원본·파생 둘 다 `does not exist` |
| 탈퇴한 쿠키로 웹 `/mypage` | 302 로그인 튕김 |

# 2. ② 로그인·탈퇴 게이트 — `users` 의존 제거

`getAccount()`가 소셜 `users` 표를 봤습니다. 그래서 **아이디/비번으로 가입한 계정(API 가입,
users 행 없음)은 웹에 로그인해도 게이트를 못 넘고, 탈퇴도 못 했습니다.**

→ **판정 기준을 `accounts`(+`auth_methods`)로 교체.** `status='active'`만 통과.
반환 모양 `{provider, nickname}`은 유지해 템플릿("○○로 로그인됨" 카드)이 그대로 읽습니다.
최근 쓴 로그인 수단이 대표(provider: kakao|google|naver|**id**). `PROVIDER_KO`에 `id: "아이디"` 추가.

인라인 복제 2곳(`handleMypage`·`handleLoginPage`)도 같은 헬퍼로 합류.
**`users`는 admin 회원목록 표시용으로만 남습니다**(소셜 콜백이 계속 채움 — 병존).

## 검수

| 시나리오 | 이전 | 이후 |
|---|---|---|
| **아이디/비번 계정**으로 웹 `/mypage` | 302 (진입 불가) | **200** + "아이디로 로그인됨" + **탈퇴 버튼 표시** |
| 소셜(카카오) 계정 | 200 | **200** + "카카오로 로그인됨" (dev-seed로 확인) |
| 익명 쿠키(계정 없음) | 302 | 302 (동일 — 의도) |
| 회귀 스모크 | — | **25/25** |

스모크 시드도 `users` 행이 아니라 **`accounts` 행**으로 바꿨습니다 — 게이트 교체의 자기 검증입니다.

# 3. 로컬 D1도 클린 슬레이트로 맞췄습니다

검수 중 로컬에 **옛 세션들의 QA 잔재**(자녀 13·기록 7·계정 껍데기들)가 남아 있는 걸 확인했습니다.
요청24에서 "로컬도 정리됐다"고 쓴 건 **부정확했습니다** — 그때 스크립트는 원격과 같은 21개 토큰만
지웠고, 로컬에만 있던 토큰들은 남아 있었습니다. 정정합니다.

원격과 같은 기준으로 정리했습니다 — 자녀 16토큰 전부 **연쇄 경로**(R2 포함), 껍데기는 SQL.
지금 로컬·원격 모두 **사용자 데이터 0**입니다. 이번 검수 데이터도 시드 → 전량 회수했습니다.

(부수 확인: `identifiers.child_id`가 PK-FK라 children보다 먼저 지워야 합니다 — 연쇄는 이미
올바른 순서라 문제없고, 손 SQL로 지울 때만 걸리는 함정입니다. 연쇄를 쓰라는 얘기가 또 됩니다.)

# 4. 앱 껍데기 — 코드 착수 전 결정이 필요합니다

규칙(착수 전 10개 항목 논의·확정)대로, 껍데기는 **파일을 만들기 전에** 아래를 확정하고 시작하겠습니다.
하이브리드 원칙(네이티브 카메라·생체 잠금·푸시 브리지, 자녀 전환=캐릭터 선택, 입력 30초)은 전제로 깔았습니다.

## 결정 항목 12개

| # | 항목 | 제 의견 |
|---|---|---|
| 1 | **셸 기술** — Capacitor vs 순수 Kotlin WebView | **Capacitor 권장.** 카메라·생체·푸시가 공식 플러그인으로 있고, JS 브리지를 손으로 안 짭니다. iOS 확장도 같은 코드 |
| 2 | **웹뷰가 여는 것** — 원격 URL vs 앱 내장 번들 | **원격 URL 권장.** 지금 서버렌더 HTML 그대로 씀 → 웹 수정이 앱에 즉시 반영, 스토어 재심사 불필요. 오프라인은 나중 |
| 3 | **개발 환경** — 사용자 PC에 Android Studio/JDK 있는지 | **확인 필요.** 없으면 설치부터(용량 ~10GB). 에뮬레이터 vs 실기기 테스트도 |
| 4 | **폴더 위치** | `에듀싱크\app\` 하위 권장(한 폴더=한 프로젝트 원칙 안에서 서브폴더) |
| 5 | **패키지명** — 예: `kr.eduthink.app` | 도메인 미정 상태라 확정 필요. **스토어 등록 후 변경 불가** |
| 6 | 인증 브리지 — 웹뷰 쿠키 vs 네이티브 토큰 저장 | 셸 1차는 쿠키 그대로(웹과 동일), 토큰 저장은 네이티브 화면 생길 때 |
| 7 | 카메라 브리지 — 업로드 폼과 연결 방식 | 웹 `<input type=file>`이 Capacitor에서 네이티브 카메라 열림(기본 동작). 1차는 추가 코드 0 |
| 8 | 생체 잠금 — 언제 요구 | 재인증(§4.5) 자리. 1차 셸에선 스텁, 네이티브 재인증 화면 때 구현 |
| 9 | FCM 푸시 | 1차 제외(웹푸시도 미사용 중). 자리만 |
| 10 | 자녀 전환 캐릭터 화면 | **네이티브가 아니라 웹 화면**으로 먼저(마이페이지 스위처 개편) — 목업 먼저 원칙 |
| 11 | 대상 SDK/최소 버전 | target 34 / min 26(안드로이드 8.0, 점유율 ~97%) |
| 12 | 검수 방법 — 껍데기의 "1회 검수"가 뭘 통과해야 하나 | 에뮬레이터에서 로컬 8788 접속 → 검색·학교탭·로그인·업로드 실동작 |

## 확정 (2026-07-24 답변 수신)

1. **셸 기술 = Capacitor.** TWA는 생체 잠금·카메라 브리지가 약해 정본 §4.5를 못 지켜 제외,
   RN/Flutter는 웹 재활용·저비용과 어긋나 제외.
2. **웹뷰가 여는 것 = 번들된 앱 UI(로컬 자산) + `/api/v1` 데이터.**
   기존 HTML 사이트 URL을 여는 게 아니다 — API-first로 판 이유가 이것.
   라이브 동결이라 원격 URL 의존 불가 · 셸 오프라인 동작 · 구글 "최소기능" 확실 통과.
   콘텐츠는 API라 실시간, 앱 UI 바뀔 때만 재빌드.
3. Android Studio → **제가 PC를 확인** (아래)

## ③ 개발환경 실사 결과 — **설치 필요**

| 항목 | 상태 |
|---|---|
| Android Studio | **없음** (표준 경로 C:\Program Files\Android · D:\Android · LOCALAPPDATA 전부 부재) |
| Android SDK / adb / gradle | **없음** |
| Java | **1.8뿐** — Capacitor(Android Gradle 8.x)는 JDK 17 필요. Studio 내장 JBR로 해결됨 |
| 디스크 | C: 117GB · D: 928GB 여유 — 공간 문제 없음 |

→ **Android Studio 설치가 선행돼야 합니다**(약 3GB 다운로드 + SDK ~7GB).
설치 위치는 D: 권장(용량 여유). 설치는 승인 주시면 진행합니다.

## ②(번들 UI)의 함의 — 앱 화면을 새로 만듭니다

번들 UI 확정은 곧 **서버렌더 HTML을 재사용하지 않는다**는 뜻입니다. 앱 화면(홈·학교탭·
자녀 전환 캐릭터 화면·기록 업로드·마이페이지)을 앱 자산으로 새로 짜고 `/api/v1`만 부릅니다.

→ **목업 먼저 원칙대로, Capacitor 프로젝트를 만들기 전에 클릭 가능한 앱 화면 목업부터**
만들어 보여드리는 순서를 제안합니다. 화면이 확정되면 그 HTML/JS가 그대로 번들 자산이 됩니다
(목업이 버려지지 않고 앱이 됩니다). Android Studio 설치는 그동안 병행하면 됩니다.

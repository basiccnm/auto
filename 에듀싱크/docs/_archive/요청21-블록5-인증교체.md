# 2. 유료 판정 — `orders`가 유일한 근거가 됐습니다

## 2.1 위치: `api_orders.js`에 `hasActivePass()` 신설

블록5에서 `orders`를 직접 조회하지 **않습니다.** 그러면 "무엇이 유료인가"의 정의가 두 곳으로 갈라지고,
상태 전이가 바뀔 때 한쪽만 고쳐집니다 — **삭제 연쇄가 두 벌이 됐던 것과 똑같은 실수**입니다.
주문 상태기계의 주인인 블록2가 판정도 소유하고, 블록5는 물어봅니다.

```js
hasActivePass(db, accountId, childId = null)
  → orders WHERE account_id=? [AND child_id=?] AND status='active' AND expires_at > now
```

**`expires_at`을 함께 보는 이유:** `active → expired` 전이를 돌리는 배치가 없습니다.
기간이 끝나도 `status`는 `'active'`로 남으므로, 만료일을 안 보면 **영구 이용권**이 됩니다.
검수 §6-③에서 실측했습니다.

## 2.2 🔴 `trial_expires_at`을 쓰지 않은 이유 — 실측으로 확인

지시하신 그대로입니다. 자녀를 등록하면 `trial_expires_at`에 **7일 무료체험** 기한이 자동으로 붙습니다.
이걸 유료 판정에 쓰면 체험자가 유료 상한을 전부 씁니다.

**실측** (주문 0건 · 체험 기한은 미래):

```
children.trial_expires_at = 2026-07-31  (미래 = 체험 중)
orders                    = 0건
→ limit_records = 20  (무료)
```

`trial_expires_at`으로 판정했으면 **1000**이 나왔을 자리입니다. 함정이 실재했습니다.

## 2.3 자녀별 과금 — 계정 단위와 자녀 단위를 나눴습니다

계약 §6.3·정본 §5가 **자녀별 과금**이라 한 덩어리 불리언으로 두면
**A 자녀에게 산 이용권으로 B 자녀 상한까지 열립니다.**

| 판정 자리 | 기준 |
|---|---|
| 자녀 수 상한 (`maxChildrenFor`) | **계정** — 유효한 이용권이 하나라도 있으면 |
| 기록 상한 (`maxRecordsFor`) | **그 자녀** — `child_id`까지 좁혀서 |

실측: 자녀A(이용권 있음) `1000` / 자녀B(같은 계정, 이용권 없음) `20`.

# 3. `AUTH_EXPIRED` / `AUTH_INVALID` 복구

`resolveOwner`가 `auth.error`를 버리고 `null`만 돌려줘서 **전부 `AUTH_REQUIRED`로 나가고** 있었습니다.
access가 30분짜리라, 앱이 refresh를 못 하고 **30분마다 재로그인**을 시키는 셈이었습니다.

실측 (만료 토큰은 개발용 키로 위조해 만들었습니다 — 30분을 기다릴 수 없어서):

| 요청 | 응답 | 앱 동작(계약 §1.3) |
|---|---|---|
| 만료된 access | **`AUTH_EXPIRED`** 401 | refresh 시도 |
| 서명 틀린 access | **`AUTH_INVALID`** 401 | 로그아웃 |
| 토큰 없음 | `AUTH_REQUIRED` 401 | 로그인 화면 |
| 정상 | 200 | — |

# 4. 쿠키-only 레거시 사용자 — 의도된 동작으로 확정

계정이 없으면 재인증 대상(수정·삭제)에서 `AUTH_REQUIRED`로 막힙니다. **의도대로입니다**(회신20 §4).
되돌릴 수 없는 요청에 신원이 없으면 안 됩니다.

주석에 근거를 박아뒀습니다 — *"막힘"이 아니라 "로그인하면 열림"*:
정본 §4 승계대로 첫 로그인 때 `accounts`가 생기며 `owner_token`이 그대로 이어지고,
그 사이에도 웹은 병존 경로(쿠키)로 계속 동작합니다.

실측: 쿠키만 있는 요청의 `DELETE /api/v1/children/{id}` → `AUTH_REQUIRED` 401.

# 5. 인증 중복 조회 제거

라우터가 `resolveOwner`로 한 번, `requireReauth`가 내부에서 또 한 번 풀어
**수정·삭제 요청마다 계정 조회가 두 벌** 돌았습니다. 요청당 1회로 내리고 결과를 아래로 넘깁니다.

`owner_token`과 `account`는 **일부러 분리해서** 넘깁니다 — 계약 §2.1 그대로
`owner_token`은 **데이터 키**(소유권 SQL), `account`는 **신원**(과금·재인증)입니다.
핸들러는 자기가 필요한 쪽만 받습니다. 소유권 검증 SQL은 한 줄도 안 바꿨습니다.

# 6. 🔴 검수 중 발견해 고친 것 — **이용권 산 자녀는 삭제가 안 됐습니다**

①에서 "`orders`는 이력이라 보존"으로 확정했는데, `orders.child_id`가 `children(id)`를 참조하기 때문에
**자녀를 지우려 하면 FOREIGN KEY 위반으로 500**이 났습니다.

```
D1_ERROR: FOREIGN KEY constraint failed: SQLITE_CONSTRAINT_FOREIGNKEY
  at deleteChildCascade (data_children.js)
```

**즉 이용권을 한 번이라도 구매한 자녀는 삭제할 수 없는 상태였습니다.** 돈을 낸 사용자만 골라서 막힙니다.
①의 검수에서 안 잡힌 이유는 **주문이 없는 자녀로만 시험**했기 때문입니다.

**조치:** `child_id`가 nullable이라 연쇄 안에서 **NULL로 끊습니다.**

```sql
UPDATE orders SET child_id = NULL WHERE child_id = ?   -- 행은 남고 링크만 끊김
```

금액·기간·계정·상태는 그대로 남아 이력이 보존됩니다 —
**회신20 §3-3의 "계정 연결 끊고 익명 보존"을 자녀 단위에 그대로 적용**한 것입니다.

실측:

| | 결과 |
|---|---|
| 주문 있는 자녀 `DELETE` | **200** `{deleted:true}` |
| 주문 행 | 남음 (`account_id=6, months=3, amount=27000, status=active`) |
| `orders.child_id` | **NULL** |

> **부작용 하나 짚습니다.** 이용권을 산 자녀를 지워도 그 주문은 만료 전까지 `active`라
> **계정 단위 판정(자녀 수 상한)은 계속 유료**입니다. 기간권이니 돈 낸 값은 한다는 쪽이 맞다고 보고
> 그대로 뒀습니다. 기록 상한은 자녀 단위라 새 자녀에게 자동으로 열리지 않습니다.

## 8.2 손대지 않은 것

- **웹(`index.js`)의 `isSubscriber`는 여전히 쿠키 판정**입니다. ②는 블록5(API) 범위였고
  웹은 병존 경로라 그대로 뒀습니다. **웹 전환 시점(계약 §8-5)에 함께 정리할 항목**입니다
- **레거시 `payments`로만 결제한 사용자**는 `orders`에 행이 없어 API에서 무료로 잡힙니다.
  현재 `payments`는 더미 2행뿐이라 실피해 없음. 계정 탈퇴 연쇄 착수 때 함께 확정하면 됩니다
- **`AUTH_SECRET`** — 여전히 개발용 상수. 배포 전 `wrangler secret put AUTH_SECRET` **필수**

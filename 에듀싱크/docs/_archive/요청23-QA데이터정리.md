# 2. 스크립트 — `scripts/qa_cleanup_2026-07-24.sh`

## 2.1 🔴 SQL 한 방으로 안 지웁니다

`DELETE FROM children`만 돌리면 **R2에 아이 사진 약 148개(74건 × 원본+썸네일)가 영구히 남습니다.**
D1에서 `image_key`를 잃는 순간 그걸 찾아낼 방법도 같이 사라집니다.

→ **자녀는 반드시 admin 연쇄 삭제 엔드포인트를 태웁니다**(`deleteChildCascade` → R2 먼저).
계정 껍데기(`users`·`accounts`·`auth_methods`·`free_trials`·`notif_settings`·`push_subscriptions`)만 SQL.

**①에서 단일 진입점을 만든 이유가 여기서 값을 냅니다** — 정리 스크립트가 삭제 로직을 다시 쓰지 않습니다.

## 2.2 와일드카드를 안 씁니다

`LIKE 'qa-%'` 같은 패턴 삭제를 쓰지 않고 **19개 토큰을 명시**했습니다.
운영 DB에서 패턴 삭제는 오폭이 조용히 일어납니다.

## 2.3 기본이 드라이런

`--apply`가 없으면 **세기만 합니다.** 실수로 실행되지 않습니다.

## 2.4 ③단계 — 옛 잔재 청소

조사 중 **연쇄가 그 표들을 안 잡던 시절(2026-07-19 이전)의 고아**를 찾았습니다.
로컬에서 `personal_events` 2건(`가족여행`·`신혼여행`, 2026-07-16자, 이미 없는 `child_id=89`).
**부모가 이미 없는 행만** 지웁니다.

> `records`는 이 단계에서 **일부러 제외**했습니다 — R2 원본이 딸려 있어 SQL로 지우면 사진이 고아가 됩니다.
> 고아 `records`가 있으면 점검에 잡히고, 그건 R2까지 함께 다뤄야 하는 별건입니다.
> (원격 점검 결과 고아 `records` **0건** — 다행히 해당 없음)

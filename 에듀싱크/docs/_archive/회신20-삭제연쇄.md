## 0. 먼저 — "정체불명 수정/삭제"의 정체
`data_children.js`가 이미 있었고(07-24 07:57~59) 로그가 없던 것 = **회신19 직후 켰다가 컨텍스트 만땅으로 갈아탄 그 세션이 작업하고 로그를 못 남긴 채 끊긴 것**으로 본다. "다른 세션이 붙어있다"기보다 **직전 세션의 미기록 작업**이다. `childId` 정수 변환·R2 로그도 그쪽 흔적.
→ 교훈: **세션은 끊기기 전 `docs/작업로그.md`·`인계-코드탭.md`를 먼저 갱신**하고 죽어야 한다. 그래야 이런 유령이 안 생긴다.

단 `--remote` 뜨자마자 찍힌 `POST /admin/members/38/delete`는 따로 짚는다:
- child 38 이미 없고 고아 0건 = **피해 없음.** 연쇄는 깨끗.
- 그래도 admin 삭제 엔드포인트가 사용자 행위 없이 --remote에 떨어진 건 위험 신호. **원인 유력: 열려 있던 admin 브라우저 탭(8788/원격)의 자동 재요청.**
- 조치: (1) --remote에 붙은 admin 탭 전부 닫기, (2) **파괴적 테스트는 무조건 `--local`, `--remote`는 읽기·검증 전용**(코드탭이 이미 그렇게 함 — 이 원칙 고정), (3) admin Basic Auth 재확인.

## 1. `community_posts` 누락 잡은 것 — 정확하다
판별 기준을 "개인 데이터로 보이는가"가 아니라 **"`child_id`를 들고 있는가"**로 못박은 것 = 이번 설계의 핵심 규칙이다. 정본 §9(child_id 검증) + "언제든 원본까지 전부 삭제" 약속과 정확히 정합. 주석 박제 승인. 이 규칙이 앞으로 새 테이블 누락을 막는다.

## 2. §2 보강 3건 — 전부 승인
- 기록 단건 삭제 인라인 → 공용 함수: 승인(단일 진입점).
- R2 실패 조용히 삼킴 → 로그: 승인. **"조용한 실패가 제일 나쁘다" 100% 동의.**
- `childId` 문자열/정수 → admin 삭제가 0건인데 302 "삭제됨": **이게 제일 위험한 종류다**(사용자는 지웠다 믿고 데이터는 남음). `Number()` 강제 + 반환값 확인 승인. 직전 세션 수정이라도 실동작 검수에 넣은 판단 옳다.

## 3. 확인 요청 3건 — 확정

**1. 커뮤니티 글 동반 삭제 — 승인(현재 구현 유지).**
`child_id`를 든 데이터라 자녀 삭제 시 파기가 원칙에 맞다. 익명화(child_id nullable)는 add-only를 깨니 지금 택하지 않는 게 맞다.
→ 단 부작용(자녀 1명만 지워도 그 명의 글 사라짐)은 **삭제 확인 화면에 "이 자녀의 커뮤니티 글도 함께 삭제됩니다" 한 줄 경고**로 막아라(놀람 차단). 커뮤니티가 커져 "글은 남기고 싶다" 수요가 실제로 생기면 그때 익명화 스키마를 별도 설계로 재검토(지금 0행이라 저위험).

**2. `orders` 보존 — 승인.**
결제 이력은 사실 그대로(계약 §7.3, add-only, 법정·분쟁 대비). 자녀 삭제로 안 지운다. 맞다.

**3. §5 계정 탈퇴 연쇄 — 별도 단계로 잡는다(QA에 묶지 말 것).**
성격이 다르다 — QA는 테스트 데이터 청소, 이건 **개인정보 파기 기능 결함**이다. "전부 삭제"라며 계정·인증·연락 데이터를 남기는 건 (a)사용자 기만 (b)파기 의무 위반 소지 → **라이브 전 필수.**
- 범위 원칙: **신원·인증·연락(`accounts`·`auth_methods`·`users`·`notif_settings`·`push_subscriptions`·`free_trials`)은 완전 파기 / 결제·신고 이력(`payments`·`orders`·`community_reports`·`info_reports`)은 계정 연결 끊어 익명 보존**(법정·남용 대응).
- 화면 문구도 실제와 일치시킬 것("계정·개인정보 삭제, 일부 거래·신고 이력은 법령에 따라 익명 보존").
- 순서: **②인증 교체로 계정 모델 확정된 직후** 착수(계정 탈퇴가 그 모델 위에 선다).

## 4. 다음 = ② 블록5 인증 교체 — §7 유의점 반영해서 GO
- **`isSubscriber`: orders 기준으로.** 지적 정확 — `children.trial_expires_at`은 7일 무료체험도 포함이라 "유료" 판정에 쓰면 안 된다. `orders status='active' AND expires_at>now`로. **이거 놓치면 무료체험자가 유료 기능을 다 쓴다.**
- **`AUTH_EXPIRED`/`AUTH_INVALID` 보존:** `resolveOwner`가 `auth.error`를 버리지 말 것. 계약 §1.3대로 앱이 refresh를 시도하게(지금은 다 `AUTH_REQUIRED`라 로그인 화면으로 튕김). 승인.
- **쿠키-only 레거시 사용자:** API 수정·삭제가 계정+재인증을 요구해 막히는 건 **의도된 동작으로 OK**(API는 인증 액션). 단 정본 §4 마이그레이션 보장 — **첫 로그인 때 `accounts` 생기고 `owner_token` 승계돼 자기 데이터 그대로 이어받기**가 되면 자연히 풀린다. 웹은 병존 경로로 계속 동작. → "막힘"이 아니라 "로그인하면 열림"이 되게.
- **인증 중복 조회 정리:** 요청당 resolve 1회로 내려서 DB 조회 2→1. 승인(성능 위생).
- **`AUTH_SECRET`:** 배포 전 `wrangler secret put AUTH_SECRET` 필수(재확인). 로컬 상수 OK.

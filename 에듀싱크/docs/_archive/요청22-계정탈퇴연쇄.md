# 0. 먼저 — 회신21 확인2 실측 (요청하신 못박기)

**"A 삭제 → B 여전히 20"을 찍었습니다.**

```
자녀A(이용권 보유)  limit_records = 1000
자녀B(이용권 없음)  limit_records = 20
        ↓ 자녀A 삭제 (주문은 child_id=NULL 고아가 됨)
자녀B               limit_records = 20      ← 누수 없음 ✅
계정 자녀수 상한                  = 3        ← 만료까지 유료 유지 (합의대로)
```

고아 주문(`child_id IS NULL`)은 per-child 질의(`AND child_id = ?`)에 절대 걸리지 않습니다.
**per-child 상한 누수 0. 계정 차원 혜택만 만료까지 유지.** 확인2 이대로 확정 부탁드립니다.

# 1. 🔴 착수 전 같은 FK 함정을 하나 더 찾았습니다

계정 탈퇴 표들의 스키마를 훑다가 **자녀 삭제 쪽에 남아 있던 같은 종류의 폭탄**을 발견했습니다.

```
community_reports.post_id  INTEGER NOT NULL REFERENCES community_posts(id)
```

①에서 `community_posts`를 연쇄에 넣었는데, **신고당한 글이 있으면** 그 글을 지울 때
FK 위반으로 자녀 삭제 전체가 500이 났습니다. 실측했습니다:

```
신고 있는 자녀 삭제 → HTTP 500
```

**즉 "글을 썼고 그 글이 신고당한 자녀"는 삭제가 불가능했습니다.** ①·②의 검수에서 안 잡힌 이유는
신고가 달린 글로 시험하지 않았기 때문입니다.

**조치:** `post_id`는 NOT NULL이라 `orders`처럼 NULL로 끊을 수 없습니다 → **글보다 먼저 지웁니다.**

```sql
DELETE FROM community_reports WHERE post_id IN (SELECT id FROM community_posts WHERE child_id = ?)
DELETE FROM community_posts   WHERE child_id = ?
```

> 회신20 §3-3의 "신고 이력 익명 보존"과 충돌하지 않습니다. 거기서 끊을 연결은
> **`owner_token`(신고자)**이지 **`post_id`(대상)**가 아닙니다. 대상 글이 사라지면
> 그 글을 가리키던 신고는 가리킬 대상이 없습니다. 두 경우를 §4-③에서 따로 실측했습니다.

수정 후 재측정: **302 정상 + 글·신고 함께 0.**

# 2. 설계 — 왜 `accounts` 행을 지우지 않고 비우는가

이게 이번 단계의 핵심 판단입니다.

```
orders.account_id  INTEGER NOT NULL REFERENCES accounts(id)
```

`accounts` 행을 지우면 둘 중 하나입니다:
- **(a)** FK 위반으로 탈퇴 자체가 실패하거나
- **(b)** 주문 이력을 함께 지워야 하는데, 그건 "결제 이력 보존"에 정면으로 어긋납니다

→ **묘비(tombstone)로 남깁니다.** 스키마가 이미 `status = active | suspended | withdrawn`을
두고 있습니다 — **원래 설계된 모양**입니다.

| 남는 것 | 지워지는 것 |
|---|---|
| `accounts` 행 1개 (`status='withdrawn'`) | `display_name` · `email` · `phone` · `birth_ymd` · `last_login_at` → **전부 NULL** |
| `orders`(FK 유지) | `auth_methods` **전멸** — 소셜·아이디·휴대폰 어느 것으로도 못 들어옴 |
| | `owner_token` **회전** — 옛 쿠키가 이 계정에 다시 닿지 못함 |

**사람을 식별할 값이 하나도 안 남으므로, 주문이 이 껍데기에 붙어 있어도 익명입니다.**

이건 회신21에서 두 번 데인 교훈의 일반형입니다 —
> **"보존하기로 한 표가 FK로 물려 있으면 '안 지운다'만으로는 안 끝난다. 연결을 끊어야 끝난다."**

## 2.1 단일 진입점 — `data_accounts.js` 신설

`data_children.js`와 같은 원칙입니다. 흩어놓으면 표가 늘 때 한 곳을 빠뜨리고,
그러면 "전부 삭제했습니다"가 다시 거짓말이 됩니다.

층이 다릅니다 — `deleteChildCascade`는 **자녀 단위**, `withdrawAccount`는 **계정 단위**로
자녀 연쇄를 전부 돌린 뒤 그 위에 계정·인증·연락을 얹어 파기합니다.

파일 안에 **표를 두 목록으로 못박아 뒀습니다.**
`owner_token`을 가진 새 표를 만들면 반드시 둘 중 하나에 넣어야 하고,
*"어느 쪽인지 못 정하겠으면 그건 아직 그 표의 성격을 안 정한 것"*이라고 적어 뒀습니다.

| 완전 파기 (신원·인증·연락) | 익명 보존 (결제·신고) |
|---|---|
| `users` · `notif_settings` · `push_subscriptions` · `free_trials` · `auth_methods` · `revoked_tokens` · `accounts`의 PII | `payments` · `community_reports` → 익명 토큰으로 덮어씀<br>`info_reports` → `owner_token` **NULL**(nullable)<br>`orders` → 묘비 계정에 유지 |

**순서가 안전입니다.** ①자녀 연쇄(R2 먼저) → ②이력 익명화 → ③신원 파기.
익명화를 계정 비우기보다 **먼저** 해야 합니다 — `owner_token`을 회전한 뒤엔
어느 행이 이 사람 것이었는지 알 방법이 없습니다.

## 2.2 익명 토큰을 계정 묘비와 이력이 공유합니다

일부러 그렇게 뒀습니다. 껍데기에 식별 정보가 없으므로 연결돼 있어도 익명이고,
대신 *"이 결제들과 이 신고들이 같은(누군지 모를) 사람 것"*이라는 사실이 남아 남용 대응에 쓸 수 있습니다.
**옛 `owner_token`은 시스템 어디에도 안 남습니다** = 사용자의 옛 쿠키로 아무것도 못 찾습니다.

# 3. 화면 — 실제와 일치시켰습니다

`/mypage/purge`가 이제 **계정 탈퇴**입니다. 화면이 그렇게 말하게 고쳤습니다.

| 이전 | 이후 |
|---|---|
| 메뉴 "자녀·데이터 전체 삭제" | **"회원 탈퇴"** · 설명에 "계정·자녀·원본 사진까지" |
| 제목 "정말 전부 지울까요?" | **"정말 탈퇴할까요?"** |
| 목록에 계정·연락 없음 | **"계정과 로그인 정보 — 다시 로그인할 수 없습니다"** · "알림 설정·푸시 등록 등 연락 수단 전부" 추가 |
| 남는 것에 대한 안내 없음 | **"이건 남습니다"** 블록 신설 — 결제·신고 이력은 법령에 따라 보관하되 **연결을 끊어** 보관한다고 명시 |
| 완료 문구 "전부 삭제했습니다" | **"탈퇴 처리했습니다"** + 익명 보존 사실 안내 |

탈퇴 완료 시 **쿠키를 즉시 만료**시킵니다(`Max-Age=0`).

## 3.1 🔴 부수 발견 — 자녀 없는 회원은 탈퇴할 방법이 아예 없었습니다

마이페이지의 탈퇴 진입점이 `kids.length ?` 로 걸려 있어서
**자녀를 등록하지 않은 회원에게는 버튼 자체가 안 보였습니다.** 조건에 계정을 더했습니다.

# 4. 검수 결과 — 전부 통과

`--local`로 돌렸습니다. 끝나고 `--remote` 복귀.
파기/익명보존 대상 표를 **한 행씩 전부 채운 뒤** 탈퇴시켰습니다(빠진 표가 드러나게).

## ① 완전 파기 — 전부 0

`children` · `records` · `identifiers` · `personal_events` · `community_posts` ·
`users` · `notif_settings` · `push_subscriptions` · `free_trials` · `auth_methods`
**모두 0.** R2 원본·파생(`_t`) 둘 다 `The specified key does not exist`.

## ② 계정 묘비

```
status = withdrawn
display_name / email / phone / birth_ymd / last_login_at = 전부 NULL
owner_token = withdrawn-9e…  (회전됨)
auth_methods = 0             (로그인 수단 전멸)
```

옛 `owner_token`으로 `accounts`를 찾으면 **0건**.

## ③ 익명 보존 — 행은 남고 연결만 끊김

| 표 | 결과 |
|---|---|
| `payments` | 익명 토큰 1건 / 옛 토큰 **0** |
| `orders` | **1건 유지** — `months=3, amount=27000, status=active` 그대로, `child_id`만 NULL |
| `info_reports` | `owner_token` **NULL** / 옛 토큰 0 |
| `community_reports` — **남의 글을 신고한 기록** | 익명 토큰 **1건 보존**, 신고당한 남의 글은 **그대로** |
| `community_reports` — **내 글이 신고당한 기록** | 글과 함께 삭제 (§1) |

마지막 두 줄이 §1에서 말한 "두 경우"입니다. 각각 따로 시드해서 확인했습니다.

## ④ 탈퇴 후 재접근

| | 결과 |
|---|---|
| 옛 쿠키로 `/mypage` | **302** → 로그인으로 튕김 |

| 로그인 | `findAccountByToken`·`findAccountByAuth`가 이미 `status='active'`만 조회 — 묘비는 안 잡힘 |

## ⑤ 회귀

# 5. 확인 요청 3건

1. **`accounts` 묘비 방식** — §2. `orders.account_id` FK가 NOT NULL이라 불가피했고,
   스키마의 `status='withdrawn'`이 원래 그걸 상정한 것으로 읽었습니다. 승인 필요

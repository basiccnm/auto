# 1. 결론 먼저

**뜯을 것은 생각보다 작고, 살릴 것은 큽니다.**

| | 규모 | 판정 |
|---|---|---|
| **껍데기** (layout·탭바·푸터·FAB) | 약 **150줄** | 🔴 전부 재작성 |
| **콘텐츠** (페이지 23개 본문) | 약 **2,900줄** | 🟢 살림 — 단 "본문 조각"으로 분리 필요 |
| **라우터** (index.js 분기 73개) | 약 **250줄** | 🟡 구조 유지, 화면 전환만 추가 |
| **핸들러·DB·NEIS** | 약 **2,800줄** | 🟢 손 안 댐 |

**결정적 사실**: 페이지 함수 23개가 전부 **`return layout({ title, body })`** 형태입니다. `body`가 순수 HTML 문자열이라, **`layout()`만 새로 짜면 본문 23개는 그대로 얹힙니다.** 화면마다 뜯을 필요가 없습니다.

# 2. 지금 껍데기의 정체

```js
function layout({ title, body, dark, noFooter, desc, canonical, noShare }) {
  return `<!DOCTYPE html>
  <head> …메타·OG·파비콘·Pretendard·공통CSS… </head>
  <body>
    <div class="wrap">      ← 여기가 전부
      ${body}
      ${siteFooter()}
    </div>
    ${shareFab()} ${captureScript()} ${confirmModal()}
  </body>`;
}
```

**`.wrap` 하나가 껍데기의 전부입니다.**
```css
.wrap{ width:100%; max-width:480px; margin:0 auto; min-height:100vh; }
@media(min-width:768px){ .wrap{max-width:720px} }
@media(min-width:1024px){ .wrap{max-width:960px} }
```

→ **v5가 지적한 "웹사이트 껍데기"가 정확히 이것**입니다. 가운데 칼럼 하나에 본문을 세로로 붓고, 화면이 커지면 칼럼만 넓힙니다. **화면 전환·스택·하단탭이 없습니다.** 모든 이동이 `<a href>` 풀 페이지 리로드입니다.

## 반응형 현황 — v5 "PC/모바일 분리"와 정면 충돌
지금은 **미디어쿼리 3단계로 한 벌**을 씁니다. v5가 요구하는 HTS/MTS 분리를 하려면 이 구조 자체를 버려야 합니다.

# 3. 뜯을 것 (약 150줄)

| 대상 | 줄수 | 왜 뜯나 |
|---|---|---|
| **`layout()`** | ~60 | `.wrap` 단일 칼럼 = 웹사이트 골격. 앱형 프레임(헤더+본문+하단탭+스택)으로 재작성 |
| **`tabBar()`** | ~18 | 학교 상세 전용 **상단 가로탭**(학교정보·일정·시간표·급식·커뮤니티). 앱은 **하단 탭바**가 표준이라 위치·역할이 바뀜 |
| **`siteFooter()`** | ~25 | 웹 푸터(사업자정보·약관). 앱형에선 설정 화면으로 이동 |
| **`shareFab()`** | ~20 | 전역 주입 FAB. 화면마다 다른 액션이 필요해 프레임에 편입 |
| **`.wrap` CSS** | ~10 | 미디어쿼리 3단계 → PC/모바일 분리로 대체 |
| 라우터 화면 전환 | ~20 | 지금 전부 풀 리로드. 스택 내비 도입 시 History API 필요 |

## 뜯되 살려야 하는 것 (layout 안에 섞여 있음)
- **SEO 메타** — OG·트위터·canonical·구글/네이버 인증 (색인에 필요)
- **파비콘·manifest·theme-color** — 홈화면 추가·앱 껍데기에 필요
- **Pretendard 폰트 + 공통 CSS 리셋**
- `captureScript()` — 이미지 저장(시간표·달력)
- `confirmModal()` — 전 화면 공용 확인 다이얼로그

→ **새 layout에 그대로 옮기면 됩니다.** 버리면 안 됩니다.

# 5. 라우터 (250줄, 구조 유지)

```js
async fetch(request, env) {
  const path = url.pathname;
  if (path === "/") return handleHome(...);
  if (path === "/records") return handleRecordsPage(...);
  … 73개 분기 …

```

**평평한 if 체인**입니다. 읽기 쉽고 문제없습니다. **핸들러는 전부 그대로 씁니다.**

바뀌는 건 **화면 전환 방식**뿐입니다. 지금은 모든 이동이 풀 페이지 리로드인데, 앱형 스택 내비(밀어서 들어가고 뒤로 나오기)를 하려면 History API + 부분 렌더가 필요합니다.

# 6. 🔴 결정이 필요한 것

## Q1. 화면 전환을 어디까지 앱처럼 할까요?

| 안 | 방식 | 대가 |
|---|---|---|
| **(A) MPA 유지 + 하단탭** | 지금처럼 풀 리로드, 껍데기만 앱처럼 | 구현 **가장 쉬움**. 전환 시 깜빡임, "앱 같지 않다"는 느낌 남음 |
| **(B) 부분 SPA** | 하단탭 전환은 fetch로 본문만 교체, 나머지는 리로드 | 중간. History API·스크롤 복원 필요 |
| **(C) 전면 SPA** | 모든 이동을 클라이언트 라우팅 | **앱에 가장 가까움**. 서버렌더 장점(SEO·초기속도) 상실, 사실상 재작성 |

> **코드탭 의견: (B).** v5가 원하는 "눌러 들어가고 뒤로 나오기"의 체감은 **하단탭 전환**에서 대부분 나옵니다. 상세→목록 같은 이동은 리로드여도 어색하지 않습니다.
> (C)는 SEO를 버리는 결정입니다 — 어제 robots를 열고 sitemap을 제출해 색인이 시작된 상태라, 신중해야 합니다.

## Q2. PC/모바일 분리를 코드에서 어떻게 할까요?

| 안 | 방식 |
|---|---|
| **(A) 서버 분기** | User-Agent로 판별해 `layoutMobile()` / `layoutPc()` 중 하나 렌더 |
| **(B) 경로 분리** | `/m/*` 와 `/pc/*` 를 따로 두고 리다이렉트 |
| **(C) 같은 URL, CSS로** | 지금 방식 유지 — **v5 취지에 어긋남** |

> **코드탭 의견: (A).** 같은 URL을 유지해 SEO·공유 링크가 안 깨집니다. UA 판별이 100%는 아니라 **수동 전환 링크**("PC 버전으로 보기")를 함께 두면 됩니다.
> (B)는 링크가 두 벌이 되고, 어제 제출한 sitemap과 canonical이 꼬입니다.

## Q3. `schoolDetailPage` 탭 5개를 분해할까요?

지금 한 함수(~700줄)가 탭 5개를 전부 그립니다. 앱형 하단탭으로 가면 **탭마다 독립 화면**이 되어야 합니다.

- **(A) 지금 분해** — 껍데기 재구축과 함께
- (B) 껍데기 먼저, 분해는 나중
- (C) 분해 안 하고 지금 구조 유지

> **코드탭 의견: (A).** 나중에 하면 새 껍데기 위에 옛 구조를 얹었다가 다시 뜯게 됩니다. 다만 **가장 큰 작업 덩어리**입니다.

## Q4. 하단 탭바에 뭘 넣을까요?

앱형 하단 탭바는 보통 3~5개입니다. 후보:
`홈(학교검색)` · `우리학교`(현재 자녀 학교 바로) · `기록` · `방과후` · `마이페이지`

**기록·방과후는 `FEATURE_RECORDS` OFF면 숨겨야** 하는데, 그러면 탭 개수가 변합니다. 이 처리 방식도 정해주십시오.

# 7. 착수 순서 제안 (승인 후)

1. `layoutMobile()` 신규 — 헤더+본문+하단탭 프레임, 기존 메타·폰트·스크립트 이식
2. 하단 탭바 컴포넌트
3. 페이지 23개를 새 layout으로 전환 (본문은 그대로)
4. `schoolDetailPage` 탭 분해
5. `recordsPage`·`activitiesPage`의 sticky 헤더를 새 프레임에 맞게 수정
6. PC layout은 그다음 (v5 순서: 모바일 → PC → 앱)

**1~3은 기능 변화 없이 껍데기만 교체**라 회귀 위험이 낮습니다. 4가 가장 큽니다.

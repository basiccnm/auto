# 블록1 「자녀기록」 화면 설계

작성: 2026-07-19 · 근거: `블록1-지시서-v4.md` 2절 · `mockups/블록1-목업-v1.html`(시각 정본) · 실제 코드 실사(`index.js` 2,531줄 / `templates.js` 2,590줄)
범위: **설계만.** 이 문서 작성 시점에 `workers/` 아래 코드는 한 줄도 수정하지 않았다.

구현 순서(전략 세션 지정): **①자녀 프로필 → ②마이페이지 뼈대 → ③업로드+R2 → ④타임라인 → ⑤방과후**

> 원칙: 순수 JS + 문자열 템플릿. 새 프레임워크·빌드 도구 없음. 색은 `C` 토큰, 글자는 `clamp()`, 이스케이프는 `escapeHtml()`, 페이지는 `layout({title, body})`로 감싼다. **360px 기준으로 먼저 완성**하고 큰 화면은 `layout()`의 `.wrap` max-width(480/720/960)가 알아서 넓힌다.

**목업과 현행의 차이 3곳 (모두 목업이 우선):**
1. 목업 ④에는 **별명(nickname) 칸이 없다.** 현행 폼은 별명이 필수(`nickname` NOT NULL 관례). → **이름을 받고 별명은 자동 생성**한다: 별명 = 이름 그대로 저장하되, 커뮤니티 표시에는 `community_nickname`을 쓰므로 실명 노출 위험 없음… **은 위험한 판단이다.** `children.nickname`은 헤더 스위처·`mypagePage`에 그대로 찍히고 identifiers 분리 원칙(v4 3절 "children에 이름 저장 금지")을 정면으로 어긴다.
   → **결론: 별명 칸은 유지하되 기본값을 자동 채움**한다(첫째/둘째/셋째 = 등록 순서). 목업의 "이름" 칸 아래에 접힌 형태로 "표시 별명" 한 줄 추가. 목업의 시각적 밀도를 지키면서 스키마 원칙도 지킨다. → **미결 Q1** (사장님 확인 필요).
2. 목업 ④ 하단 "등록하면 **1주일 무료 체험**이 시작돼요" — `작업로그.md` 6절에서 **개방 기간 중엔 이 문구를 쓰지 않기로 확정**(사실과 다름). 목업 v1은 그 결정 이전 캡션이다. → 개방 중이면 "🎁 개학 전까지 무료" 문구로 대체.
3. 목업 ④ 상단 배지 "🎁 지금 등록하면 1주일 무료"(`templates.js:1847`)도 같은 이유로 개방 중엔 교체.

**데이터**

| 읽기 | 쓰기 |
|---|---|
| `schools`(slug→id, name, school_kind, office_code, school_code, **sem2_start**) · `school_details.grade_breakdown`(반 수) · NEIS `classInfo` 폴백 | `children`(+`birth_year`, `consent_at`) · `identifiers`(child_id, name, created_at) · `free_trials` |

### 2.1 이미지 서빙 — `GET /records/img/:id`

**설계 원칙: `image_key`의 UUID는 인증 수단이 아니다. URL에 UUID를 노출하지 않는다.**

```
경로 파라미터 = records.id (INTEGER, 추측 가능) ← 일부러 이렇게 한다
```
UUID를 URL에 넣으면 "이 URL을 아는 사람 = 권한자"라는 잘못된 모델이 슬금슬금 생긴다(카톡 공유 한 번이면 끝). 추측 가능한 연번을 쓰고 **매 요청 소유권을 검증**하면, 인증이 유일한 방어선이라는 게 코드에 드러난다.

검증 순서(하나라도 실패 → **404**, 403이 아니다. 존재 여부 자체를 숨긴다):

1. `needsLogin` 게이트 통과 → `getAccount(db, request)` 있음 (소셜 로그인 필수, v4 1-4)
2. `owner_token` 쿠키 존재
3. 단일 쿼리로 소유권 + 키를 함께 확인:
   ```sql
   SELECT r.image_key FROM records r
     JOIN children c ON c.id = r.child_id
    WHERE r.id = ? AND c.owner_token = ?
   ```
   → `owner_token → child_id → record` 사슬이 SQL 한 줄에 박힌다. 두 쿼리로 나누면 나중에 누가 한쪽만 고친다.
4. `env.RECORDS.get(image_key)` → 없으면 404

응답 헤더:
```
Content-Type: image/jpeg
Cache-Control: private, max-age=3600      ← private 필수. CDN·프록시 공유 캐시 금지
Content-Disposition: inline
```
`no-store`가 아니라 `private, max-age=3600`인 이유: 타임라인 한 화면에 20장이 뜬다. 매 스크롤마다 R2를 다시 때리면 느리고 비싸다. `private`이면 그 브라우저에만 남는다.

**`ETag`/`If-None-Match`**: R2 객체는 불변이므로 `object.httpEtag`를 그대로 내보내고 304를 지원한다. 재방문 시 R2 GET 요금이 0이 된다.

## 3. 업로드 파이프라인

### 3.1 브라우저 (지시서 v4 1-10 / 5절-1)

```
input[type=file][multiple][accept="image/*"]
  → 각 파일: createImageBitmap → canvas(긴 변 2000px 상한, 비율 유지)
  → canvas.toBlob('image/jpeg', 0.85)
  → FormData에 files[] 로 append
```
- 긴 변이 이미 2000px 이하면 리사이즈하지 않고 **그래도 JPEG 재인코딩**한다 — HEIC/PNG 스크린샷이 섞여 들어오는 걸 서버가 감당하지 않게 한다.
- EXIF 방향: `createImageBitmap(file, {imageOrientation:'from-image'})`. 이걸 빼면 아이폰 세로 사진이 눕는다.
- **EXIF는 canvas를 거치며 통째로 사라진다** — 위치정보 제거가 공짜로 딸려온다. 이건 부작용이 아니라 기능이다("업로드 이미지에 성명·학교명이 인쇄되어 있음을 전제로 취급", v4 5절-6). 방침 문서에 명시할 것.
- 리사이즈 실패(브라우저 미지원 등)면 원본을 그대로 보낸다 → 서버 4MB 상한이 최종 방어선.

**썸네일도 같은 canvas에서 뽑는다.** 2000px JPEG 20장을 3열 그리드에 그대로 깔면 첫 화면에 6~8MB가 내려간다(360px 폰에서 한 칸이 ~110px인데). Workers엔 이미지 리사이즈가 없으므로 **업로드 시점의 브라우저가 유일한 기회**다.
- 긴 변 480px / 품질 0.7 → `files_thumb[]`로 함께 전송.
- 저장 키는 **원본 키에서 파생**: `{image_key}_t`. 스키마 변경이 필요 없다(`records`에 thumb 컬럼 없음, 마이그레이션은 이미 원격 적용 완료).
- ⚠️ **`deleteChildCascade()`가 `image_key`만 지운다**(`index.js:1356`). 파생 썸네일 키를 함께 지우도록 고치지 않으면 "언제든 원본까지 전부 삭제" 약속이 **깨진 채로** 남는다. 얼굴이 담긴 480px 이미지가 R2에 영구 잔류한다. → 리스크 R3.

### 3.2 서버 상한

| 검사 | 값 | 실패 시 |
|---|---|---|
| 파일 1장 크기 | 4MB 초과 거부 | 그 장만 스킵, 나머지 진행 + 결과 안내 |
| 한 번에 올리는 장수 | 10장 | 400 |
| MIME | `image/jpeg`·`image/png`·`image/webp`만 | 스킵 |
| 총 기록 수 | `maxRecordsFor()` | §5 |

### 3.3 R2 키 구조

```
rec/{child_id}/{uuid}         ← 원본.  image_key 컬럼에 이 문자열 전체를 저장
rec/{child_id}/{uuid}_t       ← 썸네일. 컬럼 없음, 원본 키 + "_t"로 파생
```
`child_id`를 접두사로 두는 이유: 고아 파일이 생겼을 때 `list({prefix:'rec/17/'})`로 **자녀 단위 대조·청소가 가능**하다. 평평한 키(`{uuid}`)면 DB 없이는 무엇이 무엇인지 영영 알 수 없다. 버킷은 비공개이고 접근은 항상 DB 검증을 거치므로 경로에 id가 있어도 노출 위험은 없다.

`uuid`는 `crypto.randomUUID()`. **경로 추측 방지용이지 인증이 아니다**(wrangler.toml 주석과 동일 입장).

### 3.4 실패 처리 — 순서가 전부

**쓰기 순서: R2 PUT → D1 INSERT.** 삭제(`deleteChildCascade`)와 같은 방향이며 이유도 같다: **복구 가능한 쪽으로 실패시킨다.**

| 시나리오 | 결과 | 판단 |
|---|---|---|
| R2 PUT 실패 | D1에 아무것도 안 씀. 사용자에게 "저장 실패, 다시 시도" | 깨끗함 |
| R2 성공 → D1 INSERT 실패 | **catch에서 방금 올린 R2 객체(+`_t`)를 즉시 delete**, 그 후 에러 반환 | 고아 없음 |
| 위 보상 delete마저 실패 | R2에 고아 객체 잔류(수 KB). **사용자에겐 안 보이고, `rec/{child_id}/` 대조로 나중에 청소 가능** | 허용 |
| 반대로 D1 먼저 했다면 | 타임라인에 **깨진 이미지 칸**이 남는다. 사용자가 매번 보고, 지워도 안 지워진다 | ❌ 금지 |

**다중 업로드는 장별 독립 트랜잭션**으로 처리한다. 3장 중 2번째가 실패해도 1·3번은 저장한다 — 전부 롤백하면 사용자는 5분간 고른 사진을 처음부터 다시 고른다. 결과는 "3장 중 2장 저장됐어요(1장 실패)"로 사실대로 알린다.

D1 INSERT는 장별로 `batch` 없이 개별 `run()`. `image_key`가 `UNIQUE`라 UUID 충돌은 INSERT가 알아서 거부한다.

### 3.5 시기 일괄 지정(백필)

시트에서 고른 학년·학기 **한 쌍을 그 배치 전체에 동일 적용**한다. 목업 ②-b의 "시기 — 3장 모두 이 시기로"가 그것이다. 종류도 배치당 1개("종류가 다른 사진은 나눠서 올려주세요"). 장별 개별 지정 UI는 만들지 않는다 — 탭 수가 3배로 늘고, 잘못 넣어도 나중에 `/records/edit`으로 고칠 수 있다.

제목 자동값: `"{학년}학년 {학기}학기 {종류}"` (예: "3학년 1학기 상장"). 같은 배치 3장이면 제목이 같아진다 — 의도된 동작이다(타임라인은 썸네일이 주인공이지 제목이 아니다).

## 4. 시기 자동 추정

### 4.1 `school_year` = 학년 정수 코드

`children.grade`는 TEXT("3"), 학교급은 `schools.school_kind`("초등학교"/"중학교"/"고등학교"). 이 둘로 코드를 만든다.

```js
// 학년 정수 코드(지시서 v4 1-12): 초1~6=1~6, 중1~3=7~9, 고1~3=10~12, 유치원 0 예약.
// 학교급이 다른 형제의 기록이 한 테이블에 섞여도 "3"이 초3인지 중3인지 구분되게 하려는 것.
const GRADE_BASE = { "초등학교": 0, "중학교": 6, "고등학교": 9, "유치원": -1 };
function gradeCodeOf(schoolKind, grade) {
  const base = GRADE_BASE[schoolKind];
  const g = parseInt(grade, 10);
  if (base == null || !(g >= 1)) return null;      // 알 수 없으면 null — 0으로 뭉개지 않는다(0은 유치원 예약값)
  if (base === -1) return 0;                        // 유치원
  return base + g;
}
function gradeLabelOf(code) {                       // 12 → "고3"
  if (code === 0) return "유치원";
  if (code <= 6) return `초${code}`;
  if (code <= 9) return `중${code - 6}`;
  return `고${code - 9}`;
}
```

> ⚠️ **`schoolYearOf()`라는 이름을 쓰면 안 된다.** `index.js:280`에 이미 있고, 전혀 다른 뜻이다(NEIS 학년도 = 달력연도 문자열 "2026"). 같은 파일에 동명 함수를 두면 import 없이 쓰는 지금 구조에서 조용히 덮어써진다. → 리스크 R4.

### 4.2 시기 추정

```js
// 업로드 시점 → {schoolYear(=학년코드), semester}. 학년은 자녀 프로필 기준(v4 4절).
// 3~8월 → 1학기 / 9~12월 → 2학기 / 1~2월 → 직전 학년도 2학기.
function estimatePeriod(schoolKind, grade, today = todayYmd()) {
  const mo = +today.slice(4, 6);
  const semester = (mo >= 3 && mo <= 8) ? 1 : 2;
  return { schoolYear: gradeCodeOf(schoolKind, grade), semester };
}
```

**1~2월이 "직전 학년도"인데 왜 학년 코드를 그대로 두는가**: 한국 학년도는 3월에 시작한다. 1~2월의 아이는 아직 **진급하지 않았다** — 3학년 겨울방학의 아이는 여전히 3학년이다. 즉 "직전 학년도"란 달력 연도가 하나 줄어든다는 뜻이고, 학년 코드는 그대로다. 여기서 코드를 1 빼면 실제와 어긋난다.
(`children.grade`는 `grade_promoted` 플래그로 사용자가 3월에 직접 올린다 — `handleChildEdit`의 `action=promote`, `index.js:1304`. 자동 진급 로직은 없다. 이 설계는 그 전제 위에 서 있다.)

**백필**: 시트의 학년 select는 현재 학년부터 1학년까지 내려간다(목업 ②-b: "3학년 / 2학년 / 1학년"). 학기는 1·2 둘 다. 사용자가 고른 값이 자동값을 덮어쓴다.

`school_year`는 `records`에 **정수로만** 들어간다. "3학년 1학기" 문자열은 `periodLabel()`이 표시 시점에 만든다.

## 5. 상한 처리 — 분기를 딱 한 곳에 둔다

> **"20건 초과 시 신규 업로드만 잠그고 열람·검색·삭제는 항상 허용"**(v4 1-2). 이 문장을 코드로 옮기는 가장 확실한 방법은 **한도 검사를 업로드 핸들러 하나에만 두는 것**이다. 조회·삭제 핸들러는 한도라는 개념을 아예 모르게 한다. 알면 언젠가 쓴다.

```js
// handleRecordUpload 안, R2에 손대기 전.
const limit = maxRecordsFor(isPaid, freeOpen);
const used  = (await db.prepare("SELECT COUNT(*) AS n FROM records WHERE child_id=?").bind(childId).first()).n;
if (used + files.length > limit) { /* 초과분만 자르거나 전량 거부 → 안내 */ }
```

| 인자 | 값 | 근거 |
|---|---|---|
| `freeOpen` | `isFreeOpenForSchool(school)` — **그 자녀의 학교** `sem2_start` 기준 | 학교별 개별 전환(작업로그 "학교별 개별 전환") |
| `isPaid` | **미결 Q2** — `isSubscriber(request)`(쿠키, QA 스위치)인가 `trial_expires_at > now`(실제 상태)인가 | 6절 R5 |

**화면 쪽**: `recordsPage`는 `used`·`limit`만 받아 표시만 한다.
- `used >= limit` → FAB 회색+🔒, 탭 시 이용권 안내 시트, 상단 경고 배너
- 그리드·검색·삭제 버튼은 **`used`와 무관하게 항상 그대로** 렌더

**삭제로 한도가 풀리는가**: 풀린다. `COUNT(*)`를 매번 세므로 21건에서 1건 지우면 다시 올릴 수 있다. 이게 "볼모로 잡지 않는다"의 실제 의미다.

**개방 기간**: `isFreeOpenForSchool`이 true면 `maxRecordsFor`가 1000을 돌려주므로 20건 한도가 자연히 사라진다. 별도 분기 불필요 — 이미 만들어둔 구조가 그대로 작동한다.

| **Q4** | 기록 **다운로드** 경로를 줄 것인가. `purgeAllPage`가 이미 "먼저 이미지를 내려받아 주세요"라고 안내하는데(`templates.js:2572`) **내려받을 수단이 없다** | 이미지 상세 뷰어에 "저장" 버튼(`Content-Disposition: attachment`). 안 만들면 그 문장을 지워야 한다 |
| **Q5** | 기존 자녀(이름·`consent_at` 없음)의 백필 UX — 기록 진입 시 강제 인터스티셜인가, 배너 유도인가 | 인터스티셜(동의 없이 등록 불가가 완료 기준) |

### 남는 위험

- **`FREE_OPEN_UNTIL` 후속**: 전역 상수는 폐기됐지만 개학일 미확보 3,699개교(29.4%)가 폴백 9/1로 동작 중이다. 기록 한도도 이 판정을 그대로 타므로, 8월 중 개학하는 미확보 학교의 자녀는 **실제보다 오래 20건 한도가 풀린 상태**가 된다. 손해는 아니지만 인지할 것.
- **R2 요금**: 20건×(원본 400KB + 썸네일 40KB) × 자녀 3명 = 자녀당 ~9MB, 무료 10GB 안에서 계정 1,000개 수준까지는 안전. Class B(읽기) 요청이 타임라인 1회 로드당 최대 20회이므로 §2.1의 `private, max-age=3600` + ETag가 비용 방어선이다.
- **동시 업로드 경합**: 같은 계정이 두 탭에서 동시에 업로드하면 `COUNT(*)` 검사를 둘 다 통과해 21건이 될 수 있다. D1엔 이를 막을 제약이 없다. 1~2건 초과는 실질 피해가 없으므로 **의도적으로 방치**한다(락을 걸면 복잡도만 오른다).

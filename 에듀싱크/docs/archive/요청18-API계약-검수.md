## 2. 실사에서 나온 좋은 소식 — 승계가 한 곳입니다

정본 §4의 "owner_token을 신원에서 데이터 키로 강등"이 **이미 절반 되어 있습니다.**

`index.js:2203~2215` (소셜 콜백)
```js
const existing = await db.prepare("SELECT * FROM users WHERE provider=? AND provider_uid=?")...
if (existing) ownerToken = existing.owner_token;                    // 기존 계정 → 데이터 키 복원
else ownerToken = getCookie(request,"owner_token") || newToken();   // 신규 → 익명 토큰 채택
```

**"소셜 신원 ↔ 데이터 키"가 이미 분리돼 있습니다.** `accounts`를 이 사이에 끼우면 끝입니다.
→ `children`·`records`·`activity_schedules`·R2 객체를 **한 줄도 안 건드리고** 무손실 이관됩니다. 회원 재설계가 예상보다 작습니다.

## 3. 🔴 계약을 쓰다 발견한 충돌 2건

### ① `school_year`가 두 테이블에서 뜻이 다릅니다

| 테이블 | 값 | 뜻 |
|---|---|---|
| `timetables.school_year` | `"2026"` | **NEIS 학년도**(달력 연도 문자열) |
| `records.school_year` | `3` | **학년 정수 코드**(초3) |

**같은 이름, 완전히 다른 개념입니다.** 앱이 이걸 헷갈리면 초3 기록이 2026년으로 표시됩니다.

→ **계약에서 시간표만 `neis_year`로 이름을 바꿔 내보냅니다.** DB는 안 건드립니다(add-only 원칙).
이 처리가 맞는지 확인 부탁드립니다.

### ② `payments`와 `orders`가 공존합니다

기존 `payments`(2행, 더미)는 `owner_token` 기준이고, 신설 `orders`는 `account_id` 기준입니다.

→ **`payments`를 읽기 전용 이력으로 동결**하고 신규는 전부 `orders`로 가는 안을 넣었습니다. 정본이 "이력은 사실 그대로"를 원칙으로 삼았기 때문입니다. 승인 여부 확인 부탁드립니다.

## 4. 🔴 트랙 편성 정정 제안

정본 §12는 **1(회원) + 3(학교정보) + 4(일정·시간표) 동시 착수**를 지시했는데, 실사해보니 **3과 4가 같은 파일을 만집니다.**

| 블록 | 파일 | 충돌 |
|---|---|---|
| 1 회원 | `auth.js` + `index.js` 인증부 + 신규 `api_auth.js` | — |
| 3 학교정보 | 신규 `api_schools.js` | — |
| **4 일정·시간표** | **위와 같은 파일** | ⚠️ **3과 동일** |
| 5 자녀·기록 | 신규 `api_records.js` | — |
| 2 결제 | 신규 `api_orders.js` | — |

**제안: 3+4를 하나로 묶습니다.** 둘 다 "학교 읽기 API"라 자연스럽고, 실제로 같은 핸들러(`handleSchoolDetail`)에서 나옵니다.

그 외에는 **전부 신규 파일로 분리**해 `index.js`엔 라우터 한 줄씩만 추가합니다. → **`index.js` 충돌 0건**으로 병렬이 가능합니다.

## 5. 계약의 핵심 설계 (검수 포인트)

### 5.1 응답 봉투를 객체로 고정
목록도 배열이 아니라 `{ items, total, cursor }` 객체입니다. 나중에 페이지네이션을 넣을 때 **앱을 안 고쳐도 되게** 하려는 것입니다.

### 5.2 `NOT_FOUND`가 권한 없음을 겸합니다
남의 기록에 403을 주면 **"그 id가 존재한다"는 정보가 샙니다.** 기존 이미지 서빙이 이미 이 규칙이라 전체로 확장했습니다.

### 5.3 재인증(step-up) 경계 — 정본 §4.5
| access만 | access + **reauth** |
|---|---|
| 조회 · **기록 업로드** · 자녀 등록 · 방과후 등록 | 기록 삭제 · 자녀 삭제 · 전체 삭제 · 정보 수정 |

**업로드에 재인증을 안 겁니다.** 정본 §0의 승부처가 "넣는 데 30초"라서입니다. 추가는 덧붙이기라 피해가 작고, 위험은 펼쳐보기·고치기·지우기에 있습니다.

### 5.4 기록 응답을 AI 입력 형식으로
```json
"period": { "school_year": 3, "semester": 1, "label": "초3 1학기" }
```
`period`를 **객체로 묶었습니다.** 블록1.5의 `grades`가 붙을 때 같은 시기 축을 공유합니다. `image_key`(R2 키)는 **절대 응답에 안 넣습니다.**

### 5.5 결제수단이 플러그
`mock` · `bank_transfer` · `pg` · `google_iap`가 **같은 상태 전이**를 탑니다. PG를 붙일 때 상태기계는 안 건드립니다. `mock`만 `pending → active`로 한 번에 갑니다.

### 5.6 날짜를 `YYYYMMDD` 문자열로 유지
ISO로 바꾸면 `academic_schedules` **219만 행을 전부 변환**해야 합니다. 문자열 비교만으로 범위 질의가 되므로 그대로 둡니다.

## 7. 확인 요청 5건

1. **가격** — `{1개월 1만, 3개월 2.7만, 6개월 5.1만, 12개월 9.6만}` (자녀 1명당)을 작업 기준값으로 넣었습니다. 정본이 "약 1만원, 열어둠"이라 해서 제가 임의로 할인율을 잡았습니다. **대표님 확정 필요**
2. **`payments` 동결** — §3-②
3. **블록3+4 병합** — §4
4. **`/api/v1/plans`를 앱에 노출할지** — 구글 정책(정본 §5 주의)상 앱에서 가격을 보여주는 것 자체는 문제없으나, 결제로 이어지면 안 됩니다. 계약엔 넣었는데 앱이 호출할지는 별개 판단입니다
5. **웹 전환 시점** — 기존 HTML 핸들러를 언제 이 API 위로 옮길지. 지금 계약은 **병존**입니다(웹 안 깨짐)

> **[현행]**
> "서비스 이용을 위한 최소 정보만 수집합니다: 자녀의 학교·학년·반·별명(**이름 미수집**), 브라우저 식별용 임의 토큰. …"

>
> **1. 수집 항목**
>
> 회사는 서비스 제공에 필요한 최소한의 정보만 수집합니다.
>
> **(가) 모든 이용자**
> · 자녀의 학교·학년·반, 별명

## 1-2. 제1조의2(업로드 이미지에 관한 특칙) — **신설**

> **1의2. 업로드하시는 이미지에 대하여**
>
> 상장·통지표·성적표 등에는 **자녀의 성명, 학교명, 학년·반, 담임 성명, 성적·평가 내용**이 인쇄되어 있는 경우가 많습니다. 회사는 이용자가 업로드하시는 이미지에 **이러한 개인정보가 포함되어 있는 것을 전제로** 취급합니다.
>
> · 업로드된 이미지 원본은 **외부에서 주소만으로는 열 수 없는 비공개 저장소**에 보관하며, 본인 인증을 거친 요청에만 응답합니다.
> · 저장 중(at-rest)과 전송 중(HTTPS) 모두 암호화됩니다.
> · 회사는 이미지 안의 글자를 읽어내거나(문자인식), 그 내용을 분석·통계·광고에 이용하지 않습니다.
> · **검색·정렬에 쓰는 정보는 보호자가 직접 입력한 제목·종류·시기뿐이며, 이미지 내용은 사용하지 않습니다.**
>
> 원본이 남는 것이 부담스러우시면 업로드 전에 이름 부분을 가리셔도 됩니다. 서비스 이용에 아무 지장이 없습니다.

## 1-3. 제1조의3(수집 근거 — 보호자 동의) — **신설**

> **1의3. 누가 동의하는가**
>
> · 자녀기록에 들어가는 모든 정보는 **법정대리인(보호자)이 서비스에 직접 입력하거나 업로드한 것**입니다.
> · **아동 본인은 이 서비스에 가입하지 않으며**, 회사는 아동으로부터 직접 개인정보를 수집하지 않습니다.
> · 자녀를 등록하실 때 **"본인은 보호자이며 자녀 기록의 등록·보관에 동의합니다"** 항목에 동의하셔야 등록이 진행됩니다. 동의 시각을 기록·보관합니다.
> · 만 14세 미만 아동의 개인정보 처리에 관한 **개인정보 보호법 제22조의2**에 따른 법정대리인 동의를 위 절차로 받습니다.
> · **출생연도는 선택 항목**입니다. 동의하지 않으셔도 서비스 제공을 거부하지 않습니다(같은 법 제22조제5항).

## 1-4. 제2조(이용 목적) — **문단 추가**

기존 문단 유지 + 아래 추가.

# 2. "내 아이 데이터, 이렇게 보호합니다" 안내 페이지

**노출 위치**: 마이페이지 → 설정 (지시서 v4 2절 ①-5)
**톤**: 학부모가 30초 만에 읽고 안심할 수 있게. 기술 용어 금지.

---

### (페이지 상단)

> ## 내 아이 데이터, 이렇게 보호합니다
>
> 아이의 상장과 성적표를 남의 서버에 올린다는 게 어떤 마음인지 압니다.
> 그래서 저희가 **무엇을, 어떻게** 하고 있는지 그대로 적어 두었습니다.

---

### ① 이름은 기록과 따로 보관합니다

> 아이 이름은 **이름만 따로 두는 별도의 공간**에 저장합니다.
> 기록(사진·제목·시기)에도, 일정에도, 서비스 기록(로그)에도 이름은 들어가지 않습니다.
>
> 화면에 "○○이의 3학년 1학기"라고 보이는 건, **그 화면을 그리는 순간에만** 이름을 잠깐 가져와 붙이기 때문입니다.
>
> 그리고 저희는 **이름으로 검색할 수 있는 길을 아예 만들지 않았습니다.** 이름을 빠르게 찾는 색인을 두지 않았기 때문에, 설령 안에서 누가 찾으려 해도 "이 아이의 이름은 무엇인가"는 알 수 있어도 "이 이름을 가진 아이는 누구인가"는 찾을 수 없습니다.

*(근거: 지시서 v4 3절 — identifiers 테이블 분리, name 인덱스 미생성. 작업로그 1절 "name 인덱스 의도적으로 없음")*

---

### ② 아이별로 칸막이가 있습니다

> 자녀를 여러 명 등록하셔도 기록은 **아이마다 완전히 따로** 보관됩니다.
>
> 그리고 **모든 조회 요청마다 "이 사람이 정말 이 아이의 보호자가 맞는지"를 확인합니다.** 주소창에 다른 번호를 넣어보셔도 남의 아이 기록은 열리지 않습니다.
>
> 자녀기록은 **소셜 로그인을 하셔야만** 쓰실 수 있습니다. 번거롭게 해드려 죄송하지만, 로그인이 있어야 휴대폰을 바꾸셔도 기록이 그대로 남고, 동시에 "누구의 기록인지"를 확실히 지킬 수 있습니다.

*(근거: 지시서 v4 5절-5 "모든 조회 owner_token→child_id 검증 + 소셜 로그인 계정 검증", 1절-4)*

---

### ③ 저장할 때도, 오갈 때도 잠가 둡니다

> 올려주신 사진은 **주소를 안다고 해서 열리는 곳에 두지 않습니다.** 인터넷에 그대로 공개되는 저장소가 아니라, **본인 확인을 거친 요청에만 열어주는 비공개 저장소**에 넣습니다.
>
> · 휴대폰과 저희 서버 사이는 **HTTPS**로 암호화되어 오갑니다.
> · 저장된 파일과 데이터베이스는 **저장된 상태 그대로 암호화**되어 있습니다.
> · 사진은 올리시는 순간 휴대폰 안에서 적당한 크기로 줄여 보내므로, 필요 이상으로 큰 원본이 서버에 쌓이지 않습니다.

*(근거: 지시서 v4 5절-1·3. 작업로그 2절 — R2 버킷 `eduthink-records`, `Public access via the r2.dev URL is disabled` 확인. 암호화는 Cloudflare R2·D1의 기본 제공 at-rest 암호화)*

> ⚠️ **문구 검토 필요**: "저장된 상태 그대로 암호화"는 Cloudflare가 플랫폼 차원에서 제공하는 것이지 **회사가 별도로 앱 단에서 암호화하는 것은 아닙니다.** 학부모에게 "우리가 한 번 더 잠갔다"로 읽히면 과장입니다. 위 문구는 주체를 흐려 두었으나, 더 정확하게 "저희가 쓰는 저장소는 저장된 상태에서도 암호화됩니다"로 바꾸는 안을 검수에서 결정.

### ④ 광고는 아이 데이터 근처에 오지 못합니다

> **마이페이지, 기록 보관함, 방과후·활동, 결제 화면에는 광고를 넣지 않습니다.** 앞으로도 넣지 않습니다.
> 광고는 급식·시간표·학교정보 같은 **공개된 정보 화면에만** 나옵니다.
>
> 광고는 화면을 만들 때 **아이 기록과는 완전히 다른 경로로** 붙습니다. 광고 코드가 기록·이름·일정을 읽어갈 수 있는 통로 자체가 없습니다.
>
> 이용권을 쓰고 계신 동안에는 **광고가 전부 사라집니다.**

*(근거: 지시서 v4 2절 ⑤ 광고 배치 규칙, 5절-4)*

> ⚠️ **구현 확인 필요**: ①현재 광고 슬롯은 **실제 애드센스 스크립트가 아니라 자리표시(placeholder)**입니다(`templates.js` `ad()`). 실제 스크립트를 붙일 때 위 약속이 유지되는지 재검증 필요. ②마이페이지·기록 화면은 아직 미구현이므로 "광고 없음"은 **약속이지 검증된 사실이 아닙니다.** 화면 구현 후 v4 완료기준 체크리스트로 확인해야 합니다.

>
> **휴지통은 없습니다.** 지우시면 저희도 되돌릴 수 없습니다. 그게 맞다고 생각합니다.

# 4. 미해결 과제 (배포 전 반드시 처리)

## 4-1. 🔴 법 제22조의2 "동의 여부 확인"을 현재 구현이 충족하지 못합니다

**법 조문**: 제22조의2제1항 — "법정대리인의 동의를 받아야 하며, **법정대리인이 동의하였는지를 확인하여야 한다**."
**시행령 제17조의2제1항**: 확인 방법 **7가지 한정 열거** — ①문자 통지 ②카드정보 ③휴대전화 본인인증 ④서면 ⑤전자우편 ⑥전화 2회 ⑦이에 준하는 방법.

**현재 설계(지시서 v4 2절 ④)**: 자녀 등록 폼의 **체크박스 1개**("본인은 보호자이며…").
→ 이는 **동의 표시**에는 해당하나, 시행령이 요구하는 **별도 확인 수단**(①~⑦)이 없습니다. **체크박스만으로는 요건 미충족으로 판단될 소지가 큽니다.**

**추가로**: 서비스는 **이메일·전화번호를 일절 수집하지 않는 설계**입니다(방침 제1조, `loginPage` 주석). 시행령의 확인 수단 7가지 중 ①②③④⑤⑥이 전부 **연락처 또는 결제수단**을 전제로 합니다. 즉 **현행 무연락처 정책과 법정 확인 의무가 정면 충돌합니다.**

**선택지 (전략 세션 결정 필요)**
| 안 | 내용 | 대가 |
|---|---|---|
| A | 자녀기록 이용 시에만 **휴대전화 본인인증** 1회(시행령 3호) | 가입 마찰 大, 인증 비용 발생 |
| B | 소셜 로그인 시 **이메일 수집 동의 범위 확대** → 동의 내용 메일 발송·회신(5호) 또는 확인 메일 통지(1호 준용) | 무연락처 원칙 포기, 카카오/네이버 이메일 제공 동의 항목 추가 필요 |
| C | **유료 결제 시 카드정보 확인**(2호) 활용 | 무료 이용자를 못 덮음 |
| D | 만 14세 미만 자녀 기록 기능 자체를 **본인인증 완료 계정에만** 개방 | 사실상 A |
| E | 현행 유지 + 리스크 감수 | **권장하지 않음** — 아동 데이터 + 이미지 원본이라 사고 시 파급이 큼 |

**참고**: 아동이 직접 가입하지 않고 보호자가 자기 계정으로 자녀 정보를 입력하는 구조라 하더라도, **처리 대상이 만 14세 미만 아동의 개인정보**인 이상 제22조의2의 적용을 벗어난다고 단정하기 어렵습니다. → **법률 자문 필요 항목**.

## 4-2. 🟡 '기타' 종류 업로드로 건강 관련 서류가 들어올 수 있음

기록 종류 6종에 '기타'가 있습니다. 이용자가 진단서·보건 관련 서류를 올리면 **법 제23조의 진짜 민감정보(건강)** 가 서버에 들어옵니다. 별도 동의 없이 처리하면 위반 소지.
**대응안**: 업로드 화면에 "건강·진료 관련 서류는 올리지 말아 주세요" 안내 1줄 + 방침에 동일 취지 명시. (기술적 차단은 불가능하므로 고지로 처리)

## 4-3. 🟡 국외 이전 고지 미포함

Cloudflare 저장 위치가 국외일 수 있음. 국외 이전 고지 항목(이전받는 자·이전 국가·이전 일시 및 방법·이전 항목·이용 목적·보유 기간)을 방침에 넣을지 결정 필요.

## 4-4. 🟡 사업자 정보 공란

개인정보 보호책임자 성명·직위, 고객센터 연락처, 대표자·주소, 통신판매업 신고번호 — **전부 미확보**(작업로그 "남은 일" 동일 지적). 방침에 연락처 없이 게시하면 그 자체로 미비.

## 4-5. 🟡 이용약관 제3조·제4조가 개정 방침과 모순됨

- 약관 제3조: "**이름 등 불필요한 개인정보는 수집하지 않습니다**" → 개정 방침과 **정면 모순**. 함께 개정 필요.
- 약관 제4조: "유료 이용권은 **자녀 수·기간별로** 판매되며" → 단일가화(3,500원, 자녀 3명 포함)로 이미 변경됨. 약관만 옛날 문구.

## 4-6. 🟡 방침 게시 시점 = 기능 배포 시점

앞서 적은 대로 **기능보다 방침이 먼저 나가면 허위 기재**, 나중에 나가면 **무고지 수집**입니다. 배포 체크리스트에 "방침 교체와 기능 플래그 ON을 같은 배포에" 를 명시해야 합니다.

# 5. 전략 세션 검수 포인트

### ① 만 14세 미만 동의 확인 수단을 어디까지 갈 것인가 (4-1) — **최우선**
체크박스만으로는 시행령 제17조의2 요건을 못 채웁니다. 그런데 확인 수단 7가지가 전부 연락처·결제수단을 전제해서, **"이메일·전화 안 받는다"는 우리 서비스의 핵심 셀링포인트와 충돌**합니다.
→ 마찰(본인인증 추가)과 법적 리스크 중 어디를 택할지, 아니면 **법률 자문을 받고 갈지** 결정 필요. 8/15 개발 완료 일정을 감안하면 **지금 결정해야 합니다.**

### ② "암호화" 표현의 수위 (2절 ③)
Cloudflare가 제공하는 저장 암호화를 **우리가 한 조치처럼 쓰면 과장**입니다. 반대로 너무 정직하게 "저장소 사업자가 암호화합니다"라고 쓰면 안심 효과가 떨어집니다.
→ 현재 초안은 주체를 흐린 중간 표현입니다. **이대로 갈지, 주체를 명시할지** 결정.

### ③ 아직 없는 기능에 대해 현재형으로 약속하는 문제
"광고는 자녀 데이터 화면에 없습니다", "이름은 분리 보관합니다"는 **화면이 구현되면 참이 될 문장**이지 지금은 아닙니다.
→ 문서를 **배포와 동시에 게시**하는 전제라면 문제없지만, 화면 구현이 밀리면 방침만 먼저 나갈 위험이 있습니다. **게시 시점을 배포에 묶는 것을 명시적으로 승인**해 주십시오.

### ④ "휴지통 없음 / 복구 불가"를 그대로 쓸 것인가
2절 ⑤의 "지우시면 저희도 되돌릴 수 없습니다. 그게 맞다고 생각합니다"는 신뢰를 크게 사는 문장이지만, **실수로 지운 학부모의 민원을 100% 방어해야** 합니다. 실제로 복구 수단이 전혀 없음이 맞다면 강력한 차별점이고, 백업에서 복구할 여지가 조금이라도 있으면 **이 문장은 거짓이 됩니다.**
→ Cloudflare D1 시점 복구(Time Travel) 기능이 켜져 있는지 확인이 필요합니다. 켜져 있으면 "DB는 일정 기간 백업에 남을 수 있다"가 사실이라 문장을 수정해야 합니다. **⚠️ 구현 확인 필요.**

### ⑤ 변경 고지를 배포 며칠 전에 띄울 것인가
현재 초안은 "배포와 동시"입니다. 통상 중요한 변경은 **시행 7일 전 사전 고지**가 권장됩니다. 다만 지시서 0절의 방침은 "**8월 중하순 조용한 배포**"라 사전 고지가 이와 충돌합니다.
→ 조용한 배포를 유지하면서 고지 의무를 채우려면 **방침 페이지에 개정 예고를 먼저 올리고(배너 없이), 배너는 배포일에** 띄우는 절충안이 가능합니다. 결정 필요.

## 4. 레이아웃 폭 통일 (구조 개선)

### 문제
`.wrap`/`.top .in`의 `max-width`가 생성기 4곳에 각각 박혀 있어서 전부 달랐다.

| 페이지 | 이전 PC 폭 |
|---|---|
| 메뉴·브랜드 | 960px |
| 레시피 | **1060px** |
| 시세 | 960px |
| 마라탕 | **700px** (브레이크포인트도 640) |

페이지를 옮길 때마다 가로폭이 튀고, GNAV만 본문보다 넓게 삐져나왔다.

### 해결 — `theme.py`에 `WRAP_CSS` 단일 상수 신설
```python
WRAP_CSS = """.wrap{max-width:520px;margin:0 auto;padding:0 14px 60px}
.top .in{max-width:520px;margin:0 auto;padding:12px 14px;display:flex;align-items:center;gap:10px}
@media(min-width:840px){.wrap{max-width:960px;padding:0 24px 60px}.top .in{max-width:960px}}"""
```

**🔴 앞으로 폭은 `theme.py` 한 곳만 고친다.** 생성기에서 `.wrap`/`.top .in`의 max-width를 다시 쓰지 말 것. (색 `CSS_VARS`·네비 `GNAV`와 같은 패턴)

**결과:** 전 페이지 모바일 520 / PC 960 통일. 브레이크포인트 840px 통일. 실측으로 8종 페이지 확인 완료.

**곁들여 조정:** 레시피 목록 그리드 5열→4열(컨테이너가 좁아져서), 마라탕 카드 3열 고정.

### `gen_preview_html.py`는 f-string이 아니다
`HEAD`가 `.format()` 템플릿이라 `{WRAP_CSS}`를 직접 못 쓴다. `/*WRAPCSS*/` 플레이스홀더 + `.replace()` 방식을 썼다(기존 `/*THEMEVARS*/`와 동일).

## 5. 애드센스 심사 대응

**현재 상태: 심사 중 (미승인).** 그래서 실제 애드센스 광고 유닛은 0개고, 수익은 카카오 애드핏 하단 배너 1개에서만 나온다.

### 고친 것 1 — 가짜 광고 플레이스홀더 주석화
`<div style="display:none">광고 영역 (애드센스)</div>`가 379개 페이지 **소스에** 남아 있었다. 심사 봇은 렌더링이 아니라 소스를 읽으므로 "광고 자리만 깔아둔 사이트"로 오해할 소지가 있었다.

→ `ad_slot()`이 꺼져 있을 때 **HTML 주석**을 반환하도록 변경:
```html
<!-- banner-slot:ad-menu-top (숨김 — 승인 후 SHOW_ADSENSE/SHOW_COUPANG_BANNER=True) -->
```
승인되면 `gen_preview_html.py` 상단의 `SHOW_ADSENSE = True` 한 줄만 바꾸면 원래 자리에 살아난다.

### 고친 것 2 — 얇은 페이지 보강
`brand_*`(1,055자)·`cat_*`(1,245자)가 목록만 있고 설명이 없어 "자동생성 저품질"로 보일 소지가 있었다.

→ `brand_intro()` / `cat_intro()` 함수로 분석 문단 추가. **brand 1,552자(+47%) / cat 1,423자(+14%)**

**🔴 원칙: DB에서 계산되는 사실만 쓴다.** 브랜드의 사업 방식·품질·원산지처럼 검증 불가한 주장은 한 줄도 안 넣는다. (`brand_origins`를 화면에서 내린 것과 같은 이유 — 실존 브랜드를 대신해 사실 주장을 하면 그 자체가 리스크)

쓰는 값: 원가율 평균/최고/최저, 같은 업종 평균과의 비교, 판매가 범위, 공정위 가맹점 수·평균매출. 문단 끝에 "재료비만 계산한 추정치" 고지 항상 붙임.

### 심사 관점 현황
| 항목 | 상태 |
|---|---|
| ads.txt · robots.txt · sitemap | ✅ |
| 소개·개인정보처리방침·이용약관 + 운영자 정보 상시 노출 | ✅ |
| 개인정보처리방침에 애드센스 쿠키 조항·옵트아웃 링크 | ✅ |
| 가짜 광고 플레이스홀더 | ✅ 제거(주석화) |
| 얇은 페이지 | ✅ 보강 |
| 출처 표기(공공누리 제1유형)·추정치 고지 | ✅ |
| 브랜드 로고 102개 게시 | ⚠️ 유지(사용자 결정 — 정보 제공 목적) |
| 자동생성 페이지 비중 높음 | ⚠️ 잔존 리스크 |

**심사 중에는 광고 개수를 늘리지 않는다.** 애드핏 현행 1개 유지.

### 승인 후 할 일 (합의됨)
1. `SHOW_ADSENSE = True`
2. **자동광고(Auto ads)부터** 켜기 — 페이지 길이 편차가 커서 구글이 알아서 조절하게 하는 게 안전
3. 수동 유닛 자리 2곳:
   - **레시피 상세 우측 고정열** — `gen_dishes.py`의 `aside.dside`에 이미 구조 있음(쿠팡+애드핏). PC 스크롤 따라다니는 최적 자리
   - **레시피 목록 인피드** — `dishes.html`의 `.grid#dgrid` 타일 사이. 애드센스 **인피드 광고** 포맷이 이 용도
4. ⚠️ **인피드는 필터/정렬 JS가 광고 카드를 건드리지 않게 예외 처리 필요.** 칩 필터·정렬(인기순/재료비/가나다)이 타일을 재배열하므로 그냥 박아두면 광고가 사라지거나 튄다
5. 애드핏은 인피드 포맷이 없다(고정 규격 배너만). 카드처럼 섞으려면 애드센스여야 함

**개수 기준(합의):** 모바일 2~3개, PC 2~3개. 애드센스는 2016년에 페이지당 3개 상한을 없앴고 지금은 "광고가 콘텐츠보다 많으면 안 된다"는 기준만 있음.

## 6. 데이터 보정중 안내 + 단가 확정도 배지

### 보정중 안내 (`WIP_NOTICE`)
브랜드 89개 + 메뉴 378개 상단에:
> 🔄 **데이터 보정 중입니다.** 재료 시세를 DB 자동 연동으로 계속 보정하고 있어서, 지금 보이는 금액이 다시 방문했을 때와 다를 수 있습니다. 표시된 재료 구성은 대체로 정확하지만, **아직 반영되지 않은 재료가 있을 수 있어** 실제 원가는 이보다 조금 높을 수 있습니다.

### 단가 확정도 배지 (`cost_confidence()` / `confidence_badge()`)
메뉴별로 **계수추정이 아닌 = 실제 조사한 단가**의 비율로 3단계.

| 배지 | 조건 | 개수 |
|---|---|---|
| 🟢 단가 확정 | 재료 전부 실제 조사한 단가 | **149개** |
| 🔵 대부분 확정 80~99% | 일부만 추정값 | 110개 |
| ⚪ 보정중 (%) | 절반 이상 추정값 | 119개 |

**판정 기준 (중요):**
- `wholesale_basis`가 `coef*` → 소매가 × 0.75~0.85로 **추정**한 도매가 = 확정 아님
- 그 외(마켓봄·현장 실거래, 네이버 조사, 미트박스, KAMIS 일일시세) = **실제 조사한 단가** = 확정

⚠️ 처음엔 `wholesale_basis LIKE '%실거래%'`로 세려 했는데 **100%인 메뉴가 378개 중 0개**라 배지가 어디에도 안 붙었다. `coef` 여부로 가르니 149/110/119로 제대로 갈린다.

## 광고(`.adfit`) 근처를 건드렸으면 — **네트워크로 확인 전엔 '완료' 금지**

**2026-07-24 실제 사고에서 나온 상시 규칙이다. 예외 없다.**

### 무슨 일이 있었나
지시서 §4-4("빈 광고 라벨 제거")를 `.adfit{display:none}` + `.adfit.on{display:flex}`로 구현했다.
그 순간부터 **광고가 한 개도 안 나왔다.** 복구까지 몇 시간 매출이 0이었다.

원인: **숨겨진 컨테이너는 레이아웃 박스가 없어 광고 스크립트가 그 자리를 건너뛴다.**
`ba.min.js`와 쿠키동기화는 로드되는데 **광고 요청 자체가 안 나갔다.**
`.on`은 광고가 떠야 붙으므로 영원히 안 붙는 닭-달걀이었다.

### 왜 눈으로는 못 잡나
- 미충전이면 원래도 아무것도 안 보인다 → **"광고가 없는 것"과 "광고가 죽은 것"이 화면상 똑같다**
- 그날 오전 "광고 뜨는 것 확인함"이라 판단한 것도 **변경 전 상태**를 본 것이었다
- 시각 확인·healthcheck·스크린샷 전부 이 버그를 못 잡는다

### 확인 방법은 이것 하나뿐
해당 페이지를 브라우저로 열고:

    performance.getEntriesByType('resource')
      .filter(e => /serv\.ds\.kakao\.com\/sdk\/banner/.test(e.name))

**이 요청이 1건 이상 나가야 정상.** 0건이면 광고가 죽은 것이다.
(`ba.min.js` 로드는 아무 증거가 안 된다 — 죽었을 때도 로드된다)
추가로 볼 것: `.adfit`에 `.on`이 붙었는지, 안에 `iframe`이 1개 생겼는지, 높이가 0이 아닌지.

### 규칙
1. `.adfit` / `ADFIT` / `ADFIT_SIDE` / `ADFIT_CSS` 의 **CSS·레이아웃을 바꿨으면**,
   배포 후 **네트워크로 banner 요청 발생을 확인하기 전까지 '완료'로 보고하지 않는다.**
2. **컨테이너에 `display:none`을 쓰지 않는다.** 숨기려면 컨테이너는 살려두고
   내부(테두리·배경·패딩·라벨)만 죽인다. 현재 `theme.py` ADFIT_CSS가 그 방식이다.
3. 새 페이지 유형을 만들면(예: 정보 코너) **그 유형에서도 요청이 나가는지 따로 확인**한다.
   공용 템플릿이라도 신규 생성기는 사각지대가 될 수 있다.
4. 광고 근처 지시에 조건이 없으면 **"컨테이너는 숨기지 않는다"를 기본값**으로 두고
   진행한 뒤 그 사실을 보고한다.

- 라이브 실측 요청 발생: `/`(홈) · `/malatang-price` · `/info_bburinkle-wonga` — 전부 iframe 1개·높이 125px
